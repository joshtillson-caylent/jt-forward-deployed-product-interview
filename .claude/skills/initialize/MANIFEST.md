# Workspace Manifest

What `/initialize` creates in a new workspace, and where each piece comes from. `scaffold.sh` is the implementation; this file is the map. When the two disagree, the script and the `manifests/` files win. Fix this doc to match.

## Resulting tree

```
<workspace>/
├── README.md                      templates/README.md            (rendered; onboard-client blocks)
├── CLAUDE.md                      templates/CLAUDE.md.tmpl       (rendered; onboard-client blocks)

├── .ai/tasks/README.md            templates/dot-ai/tasks/README.md
├── .claude/skills/<name>/         template repo .claude/skills/  (every name in manifests/skills.txt)
```

Not created by `/initialize`, because each one depends on the client:
- `case-file/source/`, `case-file/*.md` summaries, `discovery/align/*`: written by `/onboard-client`
- Engagement-level folders (`enablement/` for P1, `build/` for P2, `build/` + `service/` for P3): written by `/onboard-client` from its level overlays. The site's sidebar picks them up automatically, because they're `optional` sections in `workspace.config.js`.
- `presentations/<deck>/`: `/presentation-builder`, when a deck is actually needed
- The client's identity on the dashboard: `/onboard-client` fills the `site-identity` block
- The GitHub repo and the Evo app: created by the publish flow (Phase 5, or `/publish` later)

## Three sources, on purpose

| Source | Holds | Why it's separate |
|---|---|---|
| `templates/` (this skill) | Structure docs (README, CLAUDE.md, section READMEs, context stubs, dotfiles) and the generic site dashboard and its build scripts | The template repo's own root is client-specific (it's a worked example, with a Meridian-specific site), so structure docs and the site engine can't be copied from it. They're kept here, client-agnostic by construction. |
| `manifests/shared-files.txt` → template repo root | Generic toolkit files (role context, quality rules) | Already generic and maintained in place. An improvement there reaches every new workspace without a second copy to keep in sync. |
| `manifests/skills.txt` → template repo `.claude/skills/` | The skill library | Skills are maintained in the template repo. The list is curated so a skill doesn't ship until someone decides it should. |

## File naming in `templates/`

- A path component named `dot-<x>` becomes `.<x>` (`dot-gitignore` → `.gitignore`, `dot-ai/` → `.ai/`), so template dotfiles never act on the template repo.
- A trailing `.tmpl` is dropped (`CLAUDE.md.tmpl` → `CLAUDE.md`). Claude Code auto-loads any `CLAUDE.md` in a directory it reads, so a bare `templates/CLAUDE.md` would leak into sessions working in the template repo.

## Placeholders

Rendered by `scaffold.sh` in every `templates/` file:

| Placeholder | Value |
|---|---|
| `{{REPO_NAME}}` | Basename of the target directory |
| `{{DATE}}` | Scaffold date, `YYYY-MM-DD` |
| `{{TEMPLATE_REPO}}` | Template repo's `origin` URL, or its path if there is no remote |
| `{{TEMPLATE_COMMIT}}` | Template repo's short `HEAD` SHA, with `+dirty` appended if it had uncommitted changes |
| `{{CONSULTANT_NAME}}` / `{{CONSULTANT_EMAIL}}` | `git config user.name` / `user.email` |

An unknown `{{KEY}}` is left as-is, and `verify.sh` fails on it. So a typo in a template shows up in verification instead of shipping.

## Marker blocks

Client-specific sections are wrapped in `<!-- onboard-client:begin <key> -->` … `<!-- onboard-client:end <key> -->` (in `site/workspace.config.js`, `// onboard-client:begin <key>` … `// onboard-client:end <key>`). `/onboard-client` replaces what's between the markers and leaves the markers in place, so a re-run (a change order, a new SOW) can update the same block. The key list and what each block must contain live in `.claude/skills/onboard-client/references/marker-contract.md`. That skill ships in every workspace, so the contract travels with it.
